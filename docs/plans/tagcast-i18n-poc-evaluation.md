# Tagcast interface language: proof of concept evaluation

Status: proof of concept on branch `feature/internationalization`, not merged or released.
Baseline: `c47f2e01df2237240d60572e25af22f48558cf2a` (`origin/main`, application code of 1.3.0).
Date: 2 November 2026.

This document records what the limited proof of concept (PoC) built, what it measured and what
it means for converting the rest of the interface. Background, inventory and the original
roadmap are in [the internationalization plan](tagcast-internationalization-plan.md).

## 1. Decisions taken before the PoC

- Dutch is the first translation, reviewed by the maintainer. German, French and Spanish follow.
  Japanese comes last and is only offered after a thorough language and layout review.
- The language choice is stored by the local Tagcast server, never at iBroadcast, and must not
  overwrite any other setting. Main window and Mini Player use the same language.
- Python messages stay English for now, but machine-readable error codes are prepared so that no
  handling ever depends on translated text.
- Start with one representative component before converting thousands of strings.

## 2. What was built

**Runtime** (`src/tagcast/static/i18n.js`, 208 lines, 10.2 KB unminified)

- One collision-free namespace, `TagcastI18n`. There's no global `t`, which would be shadowed
  by 501 existing identifiers named `t`.
- `text()` returns plain text for `textContent`, attributes and toasts. `html()` escapes the
  message and every value, so only explicit `TagcastI18n.trusted()` fragments stay markup.
- Plurals use `Intl.PluralRules`. Numbers are formatted with `{{name, number}}` and
  `Intl.NumberFormat`.
- English is the per-key fallback. A failed or invalid catalog keeps English and the user's choice.
- The newest choice wins when catalog requests overlap.
- A static pass updates `data-i18n` text nodes and allow-listed attributes without rebuilding
  elements.
- `errorText()` and `failure()` translate coded errors. The English message stays as it is.
- A stored non-English choice is restored before painting, with one catalog request and a
  1.2-second safety reveal.

**Catalogs**

- `static/i18n/manifest.json` lists English (complete) and Dutch (preview).
- `static/i18n/en.json` and `nl.json` hold 107 keys and 528 English words.
- `static/i18n-en.js` is generated by `tools/build_i18n.py` with a `--check` mode, the same
  convention as `dark.css`. English is therefore always available synchronously, for the first
  paint, the fallback and the test harness.
- The format is a strict subset of **i18next JSON v4**: flat keys, `{{name}}` placeholders and
  `_one`/`_other` suffixes. The plan originally proposed an ICU subset. The i18next format needs
  no message parser and is supported by Weblate, Crowdin and Lokalise.

**Converted component: playback**

| Area | Content | Keys |
|---|---|---:|
| Sound dialog | Static texts, volume and mute, output notes and errors, device list, ARIA labels, `aria-valuetext` | 33 |
| Now playing panel and queue | Headings, empty states, plural track count, row details with "Up next", remove buttons, toasts for adding and removing, queue action menu | 30 |
| Mini Player | Owner snapshot with `language`, `direction`, 22 `labels` and an `idle` flag. Status texts are translated by the owner. | 27 |
| Settings → Interface → Language | Immediate preference: Automatic, English or Nederlands (preview) | 11 |
| Coded errors | Three server `NotConnected` messages and three browser-side queue errors | 6 |

**Server**

- `POST /api/settings/interface` stores only `interface_language` in the local `config.json`.
  Unlike the general settings save, it doesn't disconnect queue sync or close uploads.
- `/api/settings` returns the stored value.
- Catalogs under `/i18n/` are served with `Cache-Control: no-store`, like HTML, JS and CSS.
- `src/tagcast/errors.py` adds optional `code` and `params` to `ApiError`, `LibraryError`,
  `SourceError` and `ArtworkError`. `str(error)` and every existing JSON field are unchanged.

**Guardrails added to AGENTS.md:** the rules for keys, escaping, data boundaries, sorting,
fallback, persistence and switching.

## 3. Test results

All suites ran on Linux (Python 3.13, Node 22) against the PoC.

| Suite | Before | After | Result |
|---|---:|---:|---|
| `uv run --frozen pytest -q` | 870 | 879 | all pass |
| `node --test tests/*.test.cjs` | 627 | 655 | all pass |
| `node --test electron/tests/*.test.cjs` | 40 | 41 | all pass |
| `ruff check src tests tools`, `release_info.py`, `node --check`, `build_dark_css.py --check`, `build_i18n.py --check` | | | pass |

The existing English tests passed unchanged. The converted texts produce byte-identical English
output, and a dedicated test pins the exact old wording.

The new tests cover:

- **Catalog validation:** sorted keys, no markup, nesting or unescaped values, the same
  placeholders as English, every plural form the language needs, no missing or unused keys,
  static HTML text equal to `en.json`, and the generated bundle up to date.
- **Runtime:** English plurals, Dutch loading and fallback per key, escaping of hostile values,
  missing keys and values, rejected catalogs, overlapping choices, automatic selection limited to
  complete languages, restore before paint, French "zero is singular", Japanese counters,
  right-to-left direction and error codes.
- **Behaviour:**
  - Switching to Dutch during playback with an open Sound dialog and an open Now playing panel
    makes exactly two requests: the catalog and the settings save.
  - Audio source, position, pause state, volume, mute, output, queue, index, epoch and History
    are unchanged afterwards.
  - Metadata that looks like interface text ("Now playing", "Sound", "Play queue") is never
    translated, and device names stay as reported.
  - An open metadata draft keeps its form DOM and data.
- **Persistence:**
  - The server's value applies at start.
  - An older server reply can't undo a newer local choice.
  - Other tabs of the same profile follow through the `storage` event.
  - A missing catalog keeps everything working in English.
- **Mini Player:**
  - Translated labels, language and idle state.
  - Metadata passes through unchanged and template-like titles stay literal.
  - The contract keeps a fixed set of label names with bounded plain text.
- **Server:**
  - Only `interface_language` changes.
  - Queue sync and uploads aren't touched.
  - Invalid values are rejected with a code and an unchanged file.
  - Ordinary settings saves keep the language.
  - Error payloads gain codes without changing existing fields.
  - Catalogs are served `no-store`.
  - Python error text is identical to `en.json` for every code.

Chromium (Playwright, headless) on the PoC and on an unchanged copy of `c47f2e0`, both serving the
demo library with a temporary `TAGCAST_HOME`. The browser coarsens timer resolution to 0.1 ms.

| Measurement | Result |
|---|---|

| Evaluating `i18n.js` | under 0.1 ms |

| Evaluating i18next plus `i18nextICU.min.js` (91,939 bytes) | 0.3 ms |
| Evaluating today's `i18n-en.js` (7,423 bytes) | under 0.1 ms |

| First switch to Dutch, including the catalog request | 11.2 ms |

In a real browser, choosing Nederlands in Settings switched the converted texts immediately and
saved the choice. A new tab and a separate browser profile then started in Dutch from the
server's value.

Package size isn't a deciding factor. Either option adds tens of kilobytes to downloads that are
tens of megabytes. The runtime cost of both is well under a millisecond.

## 5. Own module or i18next, re-examined

| Criterion | `TagcastI18n` (as built) | i18next 26.7.1 |
|---|---|---|
| Code to maintain | 208 lines, no dependency | Vendored 50 KB UMD file plus about 60 to 100 lines of glue: escaping, static pass, Mini Player labels, persistence and error codes are needed either way |
| Updates | None needed | Major versions every few months (v21 to v26). Manual vendoring, license notice and review of each update |
| Translation safety | Catalogs can't disable escaping or reference other keys. `<` and `>` are rejected. | Catalogs can use `{{- value}}` (unescaped) and `$t()` nesting unless configured off. The default HTML escaping double-escapes with the existing `escapeHtml` pattern. |
| Interpolation and plurals | `{{name}}`, `{{name, number}}`, `_zero` to `_other` via `Intl.PluralRules` | Same, plus context, nesting, formatters and ordinal plurals |
| Error handling | English per key, warnings once, never throws, failed catalog keeps English | Comparable with `fallbackLng`, `missingKeyHandler` and `returnNull` |
| Testability | Runs unchanged in the existing vm harness. The CI validators reuse its rules. | Runs in the harness. Validation needs its own tooling. |
| Exit path | Proven: the same JSON gives identical output in i18next (`keySeparator: false`, `nsSeparator: false`, `escapeValue: false`) | |

**Conclusion: keep the own module.** It's small and deliberately limited, and safer by
construction for a code base that writes HTML through 181 `innerHTML` sinks. Because the
catalogs are standard i18next JSON and the output matches, moving to i18next later is a change
of runtime, not of translations.

Switch to i18next if Tagcast ever needs any of these:
- gender or context variants
- nested messages
- ordinal plurals throughout
- a translation platform feature that needs the real library

## 6. Answers to the evaluation questions

**Is the solution suitable for the whole code base?** Yes. The PoC covered every pattern the
inventory found: static HTML, dynamic templates, plain-text sinks, attributes and ARIA, plurals,
a sentence fragment, coded errors, a modal dialog and a second window. Still missing before a full
conversion:
- Electron main-process menus and dialogs.
- The pseudo-locale scan.
- A key-usage scanner that covers every namespace. Today it recognises the PoC's prefixes.
- A small extraction helper.

**Can the language change safely while Tagcast runs?** Yes, for the converted parts, and the
tests prove it. There's no reload. Converted views redraw only labels, the same way a play or
pause update does. Open dialogs stay open. The metadata editor isn't rebuilt and keeps its
language until it is reopened. Every future component needs one `TagcastI18n.subscribe()` that
only rewrites labels.

**Do playback, downloads, uploads and metadata drafts stay intact?**
- Playback and drafts: tested directly.
- Downloads and uploads run on the server. A switch sends no request other than the language
  save, and that endpoint has no side effects (tested). Their screens aren't converted yet.

**Is storage and synchronisation correct?** Yes, within these limits:
- The server's `config.json` is the source of truth. The profile cache only speeds up the
  first paint.
- Tabs in the same browser profile follow at once.
- Other browsers and the desktop app follow on their next start or settings reload, not live.
  A cheap re-read of `/api/settings` when a window regains focus would make that near-live. It
  adds requests, so it's left for a separate decision.
- The Mini Player always follows its owner window, within 250 ms.

**How much work is one complete component?** The playback component had about 70 existing
strings and needed 30 new label keys. The conversion itself touched 6 application files. Most
strings were mechanical. Real work went into:
- 3 plurals
- 1 sentence fragment ("Up next · ")
- 3 thrown errors
- the Mini Player contract, which mixed metadata and interface text in one field
- the tests

**How much can be automated reliably?** Of the 3,408 text occurrences in the inventory:

| Kind | Share | Handling |
|---|---:|---|
| Plain literals | 44% | Mechanical with a codemod or AI-assisted extraction, then human review |
| Static text inside HTML templates | 25% | Mechanical, then human review |
| Static HTML | 12% | Mechanical, then human review |
| Messages with placeholders | 8% | Manual restructuring |
| Fragments | 7% | Manual restructuring |
| Plurals | 4% | Manual restructuring |

Validation is fully automated by the new tests. Translation drafts can be machine-made. Native
review stays human.

## 7. Revised estimate for the complete English base

All figures are estimates for one developer with AI assistance. They replace the Phase 1 numbers
in the plan, which were 5-8 days for the foundation and 17-30 days for extraction.

| Work | Developer days |
|---|---:|
| Remaining foundation: Electron menus and dialogs, pseudo-locale scan, full key scanner, extraction helper | 2-4 |
| Extracting the remaining about 2,550 unique texts with English parity, in the batches from the plan | 12-20 |
| Python error codes for the roughly 250 messages users can realistically see (optional, infrastructure exists) | 3-5 |
| **Complete English base** | **14-24**, or 17-29 with Python codes |

The complete Dutch translation then needs about 25-35 hours of review for about 21,000 words,
plus 3-5 developer days of layout and packaged-app checks.

## 8. Known limits of the PoC

- Outside the playback component the interface is still English, also when Dutch is chosen.
  Settings says so.
- Electron menus, native dialogs and `confirm()` buttons aren't translated yet. `confirm()`
  buttons follow the operating system.
- The Mini Player shows its static English labels for the few milliseconds before the first
  snapshot.
- Server placeholders in data ("Various Artists", "Untitled album") intentionally stay English.
- `{{count}}` shows the raw number to keep today's English output. Grouped numbers need
  `{{count, number}}`.
- The Dutch wording needs the maintainer's review, in particular "nummer" versus "track" and
  "Apparaten" for the Devices dialog, which isn't translated yet.

## 9. Recommended next steps

3. Finish the remaining foundation items.
4. Convert the rest of the English interface in the plan's batches, lowest risk first, with the

5. Complete the Dutch translation. German, French and Spanish follow. Japanese comes last.
